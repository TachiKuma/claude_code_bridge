# Iteration 001

## Current Understanding

本轮聚焦 root-cause 推荐的最高优先项：sidebar `send-keys -M → crossterm` 关键链路。
先摸清代码现状（Explore 子代理 + 直读），再在本机 native Windows + rmux 真跑 e2e 探明该
链路是否成立。关键背景：现有 Windows/rmux fallback（`service.py:266-290`）对 sidebar 分支
执行 `select-pane -t = ; send-keys -t = -M`，把 hit-test 全交给 Rust，依赖鼠标事件进
crossterm；而这一步从未被测过（旧测试只断言 `list-keys` 字符串）。

## Implementation Approach

方案深度取舍：本轮定位为**诊断 iteration**，不写生产代码。理由（按
solution-depth-conventions）：sidebar 修复方向依赖一个未验证的前提——「send-keys -M 能把
鼠标送进 crossterm-Windows」。在验证该前提前动 hit-test / 坐标属于「在赌输入格式」，风险高
（root-cause §5 第 2 条明令禁止先改坐标）。因此本轮用真实 rmux + 真实 sidebar binary +
`SidebarMouseProbe` 建立可观测的前台派发证据，替代负向 `list-keys` 断言。

替身说明：ccbd socket 用 bogus pipe（外部边界，sidebar set_error 后仍渲染，不影响输入链路
观测）；ccb 用 stub .cmd（外部边界，避免真实 kill/config-ui）。均为边界替身，非核心逻辑降级。

## Verification Evidence

全部为本机 fresh 真跑（rmux 0.9.0 + `bin/ccb-agent-sidebar.exe`）：

1. sidebar 可在 rmux pane 内独立运行，probe 机制可观测 crossterm 事件（E1）。
2. **detached pane：send-keys 键盘+鼠标均不投递**；权威 `scripts/probe_rmux_capability.py`
   的 `capture-pane.json` 独立印证 echo 不回显、`attach-session` unsupported（E2）。
3. `-CC` 无头 attach 后 send-keys 投递恢复（shell echo 出现）（E3）。
4. **attach 下：键盘 `c` 触发 `settings_action_observed=true`；SGR mouse（`-H`/`-l`、多列）
   始终 `event_observed=false`、`mouse_event_count=0`**（E4）。

结论：native Windows crossterm 走 console INPUT_RECORD；ConPTY 把注入键盘字节转 key record，
但不把注入的 VT SGR mouse 序列转 mouse record。**`send-keys -M` 送鼠标进 crossterm pane 的
路径在 Windows 不成立**，这很可能就是生产 sidebar 点击失败的真正根因（与 owner 2026-07-27
前台 FAIL 一致）。

## Problems Encountered

- 初次 `rmux new-session | head` 因 PIPE stdio 挂起（2min timeout）；查 memory +
  `probe_rmux_capability.py` 得知 Windows 需 DEVNULL stdio，已修正。
- 初判「crossterm 特有」被 shell 对照实验推翻（detached 下 shell 也收不到），进一步用
  `-CC` attach 才隔离出真正边界：投递需 attach + 鼠标注入不被 ConPTY 转译。
- 无 owner-stop 触发。未出现 blocker 重复。
